# 录制时自动生成校验候选（v3.6.0）

> 配套阅读：`docs/verify-and-health.md`（v3.4.1 的校验机制与 11 种校验类型）。
> 本文讲的是**怎么不用手写就能把校验加上**。

## 1. 为什么让录制器顺手写校验

v3.4.1 给回放加了步骤级结果校验（`verify`），但规格要人手写。实际用下来有个尴尬
现象：**录 60 步的流程，能正确手写出校验的通常不到 10 步**。

原因不是用户懒，而是时机不对 —— 手写校验要求你回答「我点这个按钮之后，页面到底
变成了什么样」。这件事**录制的那一刻最容易知道，事后最想不起来**。

录制器天然知道答案：它知道点之前页面长什么样，点之后又变成了什么样。所以让它在
录的时候顺手把「我观测到的变化」写成校验规格，人只做复核，比事后手写省力得多。

## 2. 快速上手

录制时加一个参数即可（默认就是开的）：

```bash
# 网页录制
python recorder.py --verify auto

# 网页 + 桌面合并录制
python record_session.py --verify auto

# 只录桌面（桌面侧只能推断窗口标题，属中置信，所以默认 all）
python desktop_recorder.py --verify all
```

| 参数 | 说明 |
| --- | --- |
| `--verify off` | 完全不生成，等同 v3.5.0 行为 |
| `--verify auto` | **默认**。只生成录制时直接观测到的高置信校验 |
| `--verify all` | 额外生成弹窗 / 加载遮罩 / 窗口标题 / 值被规范化这类中置信校验 |
| `--verify-report <路径>` | 人读报告输出位置，默认 `verify_candidates.md` |

跑完会多出一个 `verify_candidates.md`，并且在 `task_flow.json` 的步骤里出现
`verify` 字段：

```json
{
  "type": "browser", "func": "click_elem", "args": ["#btn-save"],
  "ts": 1789447617541,
  "verify": [ {"type": "url_contains", "value": "/order/detail"} ]
}
```

不用它也没关系 —— `main_task.py` 遇到没有 `verify` 的步骤就是老行为。

## 3. 六条推断规则

**所有规则都只断言「录制时真实观测到的状态」，不做任何推测。** 这是本功能的
设计红线，理由见第 9 节。

| 规则 | 触发条件 | 生成什么 | 置信 |
| --- | --- | --- | --- |
| URL 变化 | 动作前后的 URL **路径**变了 | `url_contains`（锚定新增路径段，剥掉 ID） | 高 |
| 录入回读 | 输入后读到字段值，且**等于**录入文本 | `element_value_equals` | 高 |
| 录入回读 | 读到值**包含**录入文本 | `element_value_contains` | 高 |
| 反馈文案 | 动作后出现、动作前不存在的提示文案（且不含数字/日期） | `text_present` | 高 |
| 录入回读 | 页面把录入文本规范化了（如 `1000` → `1,000.00`） | `element_value_equals`（按观测值） | 中 |
| 录入回读 | 没有探测数据可回读 | `element_value_equals`（按录入文本） | 中 |
| 弹窗出现 | 动作后出现、动作前不存在的对话框 | `element_exists` | 中 |
| 加载结束 | 动作前在加载、之后观测到已结束 | `element_absent` | 中 |
| 窗口焦点 | 桌面动作前后 3 秒内有窗口焦点事件 | `window_title` | 中 |

### 3.1 URL 变化

从 `/order/list` 点到 `/order/list/detail/88`，生成的是：

```json
{"type": "url_contains", "value": "/order/list/detail"}
```

注意末尾的 `88` **被刻意丢掉** —— 它是订单 ID，下次跑必然不同，写进去就是给自己
埋雷。同理，只变查询串（`?t=1700000000`）时**什么都不生成**，因为查询串里的值
通常带时间戳或随机数。

路径变短（比如从详情页返回列表页）也不生成：断言父级路径太弱，几乎必然通过，
没有信息量。

### 3.2 录入回读 —— 这条最值钱

「输入没进去」是确定性 RPA 最常见的静默失败：`input_text` 执行了、没报错，但字段
实际是空的，一路跑到提交才炸。

录制时探测脚本会在动作后回读该字段的值，于是：

- 回读值 == 录入文本 → 生成 `element_value_equals`（高置信）
- 回读值包含录入文本 → 生成 `element_value_contains`（高置信）
- 页面做了格式化（`1000` → `¥1,000.00`）→ 按观测到的值断言，标中置信
- 回读值为空 → **不生成校验**，报告里明确提示「页面没接受这个输入，应先修流程」
  （这种情况加校验只会把一个真问题变成一条假断言）

### 3.3 反馈文案

「点保存 → 提示保存成功」是业务上最该断言的东西。探测脚本会在动作后 0.7s 和 1.8s
各扫一次常见的提示容器（`[role=alert]`、`.el-message`、`.ant-message-notice`、
`.layui-layer-msg`、`.toast`、`.van-toast` 等），并且**要求该文案在动作前不存在**，
避免把页面常驻文字误当成反馈。

多条互不包含的文案会生成数组（全部通过才算过）：

```json
"verify": [
  {"type": "text_present", "text": "保存成功"},
  {"type": "text_present", "text": "已提交审批"}
]
```

互为子串的（「保存」「保存成功」）只留信息量更大的那条。

### 3.4 弹窗 / 加载遮罩

- 动作后新出现的对话框 → `element_exists`（用录制时算出的选择器）
- 动作前在转圈、之后确认不转了 → `element_absent`

`element_absent` 有个额外好处：它会在 5 秒内轮询，等价于「等加载结束再往下走」，
顺带解决了异步渲染的竞态。

### 3.5 桌面窗口标题

桌面动作（`click_at` / `press_keys` / `open_software` …）前后 3 秒内若有窗口焦点
事件，就用**应用名**生成 `window_title`：

```json
{"type": "window_title", "value": "企业微信"}
```

它的价值是「确认没点错窗口」—— 回放时如果目标应用没在前台，点击就会打到别的窗口
上，这类错误不校验极难定位。窗口标题含数字（如「报表2026」）时跳过，因为它不稳定。

## 4. 三档模式怎么选

**建议先用 `auto` 跑一周，再看要不要开 `all`。**

- `auto`（默认）只写高置信项。它们都是「录制时亲眼看到的事实」，回放时**几乎不可能
  因为规格本身写错而误报**。
- `all` 会多出弹窗、加载遮罩、窗口标题、值被规范化这四类。它们合理但有一点点不
  确定性 —— **回放莫名失败时优先怀疑它们**。
- `off` 完全不动流程文件，适合「我只想录，校验我自己写」。

## 5. 报告怎么读

`verify_candidates.md` 有四部分：

1. **本次结果** —— 模式、步骤数、推断出多少条候选、实际写入多少步
2. **已写入的校验** —— 逐步列出：校验类型、内容、置信级别、**依据**
3. **跳过的地方（及原因）** —— 这部分和第一部分同样重要，它告诉你「为什么某些步骤
   没有校验」，例如「反馈文案含数字/日期等易变内容，跳过：订单 12345 已保存」
4. **复核建议** —— 出错时的排查顺序

第 3 部分是本功能的态度所在：**不做的事也要说清楚原因**，而不是静默省略。

## 6. 两条硬过滤

### 6.1 易变文本一律丢弃

含数字、日期、金额的文案（「订单 12345 已保存」「2026-09-15 已同步」）第二次跑必然
不同。**这是自动生成校验最常见的误报来源**，所以一律不生成，并在报告里写明。

判定规则（`core/verify_advisor.py: is_stable_text`）：长度 2~24、不含任何数字、
不含 年月日时分秒/上午下午/刚刚、不含页脚类噪声（Copyright / 隐私政策 / ICP）、
至少含一个中文或字母。

### 6.2 敏感字段永不回读

密码框、验证码、身份证/卡号类输入**不生成任何值校验**，避免把凭证写进
`task_flow.json`。判定依据是选择器名（`password` / `pwd` / `token` / `otp` /
`captcha` / `验证码` / `密码` / `身份证` / `idcard` / `bankcard` / `cvv` …）或值本身
（11 位以上纯数字，即手机号/证件号/卡号）。

> ⚠️ **顺带发现（未修）**：录制器的 `change` 监听目前会连**密码框的明文值**一起
> 写进 `input_text` 的 `args`。这是 v3.6.0 之前就有的行为，本次没有改动它（改动会
> 影响回放语义）。如果你录的流程里有密码输入，建议改用 `credential_ref` 引用凭证，
> 别把明文留在流程文件里。

## 7. 复核与修改

自动生成的校验**宁少勿错**，但业务语义仍需你确认，典型三种情况：

| 情况 | 怎么改 |
| --- | --- |
| 提示文案换了措辞（业务改了文案） | 直接改 `text` 的值 |
| 某一步允许两种结果 | `verify` 写成数组，两条都写进去（数组是「全部通过」，需要「任一通过」就先删掉一条） |
| 回放报「页面应包含文本 X」失败，X 里有单号/日期 | 改成 `element_exists`（等某个元素出现），比断言文本稳 |

数组里删掉某一项即可，不用整个删。想整步不要校验：删掉该步的 `verify` 字段。

## 9. 设计取舍

**为什么只断言观测到的事实，不推测？**

因为一个**误报**的校验比没有校验更糟：它会把本来成功的流程打断 —— 触发重试、
重试失败后降级、最后整步失败、断点停在那里等人。用户面对的是「昨天还好好的，
今天第一步就挂了」，而根因只是某条自动生成的断言写得太乐观。

所以本功能选择「宁少勿错」：

- URL 没变就不写 URL 校验（不猜「这里应该会跳转」）
- 没回读到值就降级为中置信（`auto` 模式下不写）
- 反馈文案带数字就整条丢弃
- 没有「动作前快照」的旧版录制产物，反馈类规则直接放弃（并说明原因），不靠猜

**为什么置信度不做成模型打分？**

本机是 2 核 Pentium / 8GB / 核显，跑不动任何 VLM（详见 `docs/confidence-and-intervention.md`）。
更重要的是：这里的「置信」不是概率预测，而是**证据等级** —— 「我亲眼看到 URL 变了」
和「我猜这里会跳转」是两种东西，用规则表达比用模型打分更准确、可解释、可审计。
报告里每条候选都写了依据，就是让人能自己判断。

**为什么探测只扫固定几类容器，不做整页 DOM 差分？**

整页差分在低配机器上开销不可接受（录制时每次操作都要遍历全树），而且噪声极大 ——
时间戳、广告位、随机推荐都会让差分结果面目全非。固定容器 + 可见性判断 + 40 个节点
的扫描上限，成本恒定在毫秒级。

## 10. 已知边界与后续可做

**边界**：

1. **跨页跳转后拿不到探测**。动作引发的导航会销毁 JS 上下文，`setTimeout` 里的探测
   不会执行。但导航本身会被录成 `navigate` 事件，URL 类校验依然能推断出来。
2. **ifram 内的页面**：探测跟着注入脚本走，跨域 iframe 里也注入，但反馈容器的选择器
   列表是按主流组件库列的，自研 UI 框架可能扫不到。
3. **桌面侧只有窗口标题**一种校验。桌面的「操作结果」在屏幕上，不校验截图就没法
   断言 —— 而本机跑不了视觉模型，这是硬约束。
4. **中置信项**（弹窗/加载/窗口标题）本质是启发式，偶尔会误报。
5. **探测量是固定 0.7s / 1.8s 两个时间点**。慢于 1.8 秒才出现的提示抓不到。

**后续可做**：

- 让探测时间点可配（应对慢系统）
- 从 T1 直连层捕获到的 API 响应反推业务断言（如「接口返回 code=0」）
- 把 `verify_candidates.md` 的复核结果回写（标记「已确认 / 已删除」）形成审计留痕

## 附：v3.6.0 顺带修复

真机排查时发现 `127.0.0.1:9222` 返回 **502 Bad Gateway**，根因是本机 `HTTP_PROXY`
存在时，Python `urllib` 会把**回环地址**的请求也送进代理，代理再返回 502。表现为
「Chrome 明明开着调试端口却连不上」，且报错是 502 而不是连接被拒，极难排查。

修法：新增 `core/local_http.py`，凡对本机回环地址发起的 HTTP 请求一律显式禁用代理，
并替换了 5 处调用点（`cdp_engine` / `recorder` / `browser_launcher` ×2 / `chat_mode`）。
`e2e_v360_test.py` 的 J 组用「真起一个本地 HTTP 服务 + 假代理」做了功能级验证：
走代理必失败、走 `urlopen_local` 必成功。

> 注意：T1 直连层调用**远程**业务接口（金蝶/用友等）时**不**绕过代理 —— 那些请求
> 需要遵循用户配置的网络环境。隔离在 `core/local_http.py` 里就是为了划清这条界线。
