# 置信度驱动的自适应执行（Confidence-Driven Adaptive Execution）

> v3.5.0 新增。一句话：**让机器人在「心里没底」的那几步主动停下来问你，而不是一路错到底。**
> 零模型、零 GPU、纯 Python —— 用的是回放过程中本来就存在的客观信号。

---

## 1. 为什么需要它

### 1.1 问题：过度执行（over-execution）

传统 RPA 的失败模式不是"跑不动"，而是**跑得太自信**：某一步其实没把握（元素改了、页面没加载完、
被踢回登录页了），它依然全自动往下跑——不报错、不中断，直到最后一步对账才发现全错。

这个问题在学术界有明确名字。OS-Kairos（ACL 2025 Findings，arXiv:2503.16465，上海交大 + Meta）
把它定义为 GUI 智能体的核心可靠性问题，并给出了三组对比数据（复杂场景）：

| 策略 | 任务成功率 | 说明 |
|---|---|---|
| 全自动、从不问人（OS-Atlas-Pro-7B 基线） | **14.29%** | 盲目执行，越错越远 |
| 纯提示词请求介入 | 0% | 无效 |
| 每步都问人 | 62% | 有效，但人累死了，不可用 |
| **自适应介入（只在没把握时问）** | **88.20%** | ← 本技能采用的思路 |

**关键洞察：「何时介入」比「要不要介入」重要得多。**

### 1.2 但我们不做模型

OS-Kairos 的做法是让模型对每步输出 1~5 的置信度——这需要训练一个 7B 多模态模型
（论文的训练配置至少 3×A100 80GB）。

AutoPilot Composer 换了一条路：**用确定性的客观信号合成置信度**。这在本机环境
（2 核 Pentium / 8GB 内存 / 核显 / 32 位 Python）是唯一可行的方案，而且有三个意外的好处：

- **可解释**：每一分都能追溯到具体信号（"因为 3 个元素都匹配，所以扣 1.2 分"）
- **可复现**：同样的状态永远得到同样的分数，不飘
- **零算力**：不加载任何权重，不接任何 API

而模型的自我报告置信度反而存在已知的校准偏差（普遍过度自信）——用客观信号更可靠。

## 2. 置信度是怎么算出来的

### 2.1 信号清单（全部确定性）

| 信号 | 来源 | 方向 | 逻辑 |
|---|---|---|---|
| **Tier 层级** | tier_resolver | 基准分 | T1=4.7 / T2=4.2 / T3=3.4 / T4=1.8 |
| **定位唯一性** | 元素库探测 | ±最大 | 唯一命中 +0.5；多匹配 −1.2（可能点错）；未命中 −1.8 |
| **定位通道** | 同上 | ± | 回退内联选择器 −0.3；用了已遗忘策略 −0.6 |
| **定位策略秩** | 元素库 | ± | id/name +0.35；placeholder +0.2；css 0；xpath −0.4；css_chain −0.5；坐标 −0.8 |
| **元素健康度** | element_repo | ± | 历史稳定命中 +0.4；连续未命中 ≥3 −0.9；已遗忘 −1.5 |
| **步骤历史成功率** | step_stats | ± | `(成功率 − 0.9) × 1.5`，最高 +0.15 / 最低 −1.35 |
| **可验证性** | task_flow | + | 配了 verify +0.3（能发现失败，不会假成功） |
| **环境状态** | env_guard | 封顶 | 见下表，直接压到上限以下 |

环境异常的封顶值（无论其他信号多好，都压到这个线）：

| 环境状态 | 封顶 | 为什么这么狠 |
|---|---|---|
| `cdp_down` 调试通道断开 | 0.5 | 几乎必然失败 |
| `login` 被踢回登录页 | 1.2 | **最隐蔽**：后续几十步会在登录页上空点，不报错 |
| `error_page` 跳到错误页 | 1.0 | 页面本身不对 |
| `dialog` 意外弹窗遮挡 | 1.6 | 可能点到弹窗上 |

### 2.2 分级与动作

| 分数区间 | 级别 | adaptive 模式的动作 |
|---|---|---|
| ≥ 3.5 | 高 | 自动执行 |
| 2.5 ~ 3.5 | 中 | 自动执行（不打扰） |
| 1.2 ~ 2.5 | 偏低 | **弹窗确认**（继续 / 跳过 / 暂停） |
| < 1.2 | 极低 | **只给「跳过 / 暂停」**，不提供「继续执行」 |

真实输出长这样（这是最典型的"该犹豫"场景）：

```
  ⚠️ 步骤 12/28  [click_elem【登录】] {T2(cdp)}  置信 2.40/5 偏低 ⚠️
       [基准 4.2] T2 路径（浏览器元素定位）
       [-1.80] 元素库里没有任何定位器能匹配到元素
       [-0.30] 回退到内联选择器（元素库未生效）
```

归因行是给人看的，不是给机器看的——**"为什么低"比"有多低"更重要**。

## 3. 三种运行模式

```json
"confidence": { "mode": "shadow" }
```

| 模式 | 行为 | 适用 |
|---|---|---|
| `off` | 完全关闭，行为与 v3.4.x 完全一致 | 排障时排除干扰 |
| `shadow` | **默认**。只评分、只记录、只告警，**从不打断** | 上线初期观察（零风险） |
| `adaptive` | 低置信弹窗确认，极低置信直接暂停 | 稳定性要求高的正式流程 |

### 建议的上线路径

1. **第一周用 `shadow` 跑**：让它照常自动化，但每次运行结束会告诉你
   `置信度：平均 4.12/5（高 22 / 中 4 / 偏低 2 / 极低 0）`，以及哪几步偏低。
2. **看偏低的那几步是不是"真的该担心"**：如果都是无关紧要的展示性点击，那不用管；
   如果里面藏着"提交订单""删除""扣款"这类不可逆动作——**这就是你要的答案**。
3. **改成 `adaptive`**，让它在该犹豫时问你。

这个"先观察后介入"的路径本身就是 OS-Kairos 思想的延伸：**先量化风险，再决定治理力度。**

## 4. 配置参考

完整配置（`scripts/config.json`）：

```json
{
  "step_stats_path": "./step_stats.json",
  "checkpoint_path": "./checkpoints.json",
  "stats_min_samples": 2,

  "confidence": {
    "enabled": true,
    "mode": "shadow",
    "auto_above": 3.5,
    "confirm_below": 2.5,
    "abort_below": 1.2,
    "interactive_timeout": 60,
    "max_low_conf_streak": 3,
    "tier_base": { "T1": 4.7, "T2": 4.2, "T3": 3.4, "T4": 1.8 }
  },

  "env_guard": {
    "enabled": true,
    "login_patterns": ["/login", "/signin", "/auth/", "/sso", "passport"],
    "error_patterns": ["/404", "/500", "/502", "error.html", "not-found"]
  },

  "checkpoint": {
    "enabled": true,
    "keep": 20
  }
}
```

| 字段 | 说明 |
|---|---|
| `mode` | `off` / `shadow` / `adaptive` |
| `auto_above` / `confirm_below` / `abort_below` | 三档分界线，按你的风险偏好在这些档之间调 |
| `interactive_timeout` | 弹窗等待秒数；**超时按默认项处理**（偏低→继续执行，极低→暂停） |
| `max_low_conf_streak` | 连续多少步偏低就在日志里提醒你（shadow 模式下的预警阀） |
| `tier_base` / `strategy_adj` | 各信号的权重，可整体覆盖（默认值见 `core/confidence.py`） |
| `stats_min_samples` | 步骤战绩的样本门槛，默认 2（样本不足时不给加减分） |

### 调优建议

- **觉得太吵**（频繁弹窗）→ 把 `confirm_below` 从 2.5 降到 2.0，只有更没把握时才问。
- **觉得太松**（该问没问）→ 把 `auto_above` 提到 4.0。
- **不可逆动作要格外严** → 给那几步单独配 `verify`（+0.3 分），并在流程里把它们的
  `tier` 锁定到 T2 以上，避免走 T4 坐标路径。

## 5. 环境守卫（Environment Guard）

### 5.1 四类环境异常

| 类型 | 判定依据 | 能否自动恢复 |
|---|---|---|
| `cdp_down` | 读不到页面地址 / WebSocket 断了 | ✅ 尝试重连 |
| `login` | URL 命中登录特征 **且** 页面存在密码输入框 | ❌ **明确要求人工登录**（涉及凭证，不自动重登） |
| `error_page` | URL/标题命中错误页特征 | ✅ 回滚到上一个正常页面 |
| `dialog` | 可见模态层（`role=dialog` / Element-UI / Ant / Vant 等） | ✅ 按 Esc → 点关闭按钮 |

**防误报设计**：判断登录页时要求深检确认存在密码框。否则"正常停留在 `/login` 介绍页"
会被误判成会话过期，反而制造噪音。

**诚实设计**：会话过期时守卫**不会假装能自愈**，而是明确返回
`需要人工登录：会话已过期被踢回登录页，自动重登涉及凭证，请人工登录后用 python main_task.py 从断点续跑`。
这正是 OS-Kairos "该喊人时就喊人"的原则。

### 5.2 两档检测（平衡开销与准确）

| 档位 | 时机 | 内容 | 开销 |
|---|---|---|---|
| 浅检 | 每步执行前 | 只读当前 URL 做字符串匹配 | ~0（0~1 次往返），零误报 |
| 深检 | 失败诊断 / 重试时 | 额外探测弹窗与密码框 | 1 次 JS 求值 |

## 6. 策略轮换重试（直击「盲目执行」）

### 6.1 与旧版对比

**旧版（v3.4.x 及更早）**：失败 → 等 2 秒 → **原样重跑** → 再失败 → 再原样重跑。
在元素真的变了的情况下，这 3 次重试毫无信息增量，纯浪费时间。

**v3.5.0**：每次重试**换一种做法**。

```
     ↻ 换一种定位方式重试：「id」→「placeholder」
     ↻ 已重载页面并重新定位后重试
```

### 6.2 轮换顺序是自适应的

| 环境状态 | 第一轮 | 第二轮 | 理由 |
|---|---|---|---|
| 环境异常（登录页/错误页/弹窗） | **修环境** | 换定位器 | 在错误页面上换定位器毫无意义 |
| 环境正常 | 换定位器 | 修环境（重载页面） | 那多半是元素本身变了 |

顺序由**置信度信号里的环境状态**决定；如果首选那条路走不通（例如弹窗关不掉），
会自动退到另一条，不浪费重试次数。

### 6.3 重试次数怎么配

`max_retry` 决定最多尝试几次，轮换候选有 2 类：

| `max_retry` | 实际发生 |
|---|---|
| 1 | 不重试（无轮换） |
| 2 | 一轮轮换 |
| **3（默认）** | **两类轮换都会用上，推荐** |

## 7. 检查点与回滚（Checkpoint & Rollback）

**与 `breakpoint.json` 的分工**：

| | 解决什么 | 粒度 |
|---|---|---|
| `breakpoint.json` | 跨进程恢复：「上次跑到第几步」 | 步序 |
| `checkpoints.json` | 错误状态回退：页面已被带偏，需要退回上一个良好状态 | 页面状态 |

设计来自 *Enhancing Web Agents with Explicit Rollback Mechanisms*：**智能体一旦陷入
错误路径，后续操作就极可能不可靠**，需要显式回退机制。

实现刻意保持轻量——**只记 URL / 标题 / 时间，不截图**：
这台机器的磁盘和算力都紧张，而"页面还能不能用"一次 URL 对比就能判断八成。

- 每步成功后自动记录（环形保留最近 20 条，不会无限增长）
- 同一步重试成功后覆盖而非追加
- 桌面步骤也记录，但**回滚只对浏览器有意义**（`need_url` 过滤）

## 8. 步骤战绩（Step Statistics）

按**步骤指纹**累计成功/失败次数，给置信度提供模型没有的先验：同一份流程被反复回放的真实战绩。

```
步骤战绩：12 个步骤有记录，累计成功 34 次 / 失败 5 次
最容易失败的步骤：
  - click_elem【导出报表】  成功 2 / 失败 3（成功率 40%）
```

两个关键设计：

- **指纹只取稳定字段**（`type`/`func`/`args`/`element_ref`），忽略 `id`/`ts`/`status`。
  否则每次录制产生的随机 id 都会让统计失忆。
- **样本保护**：样本数 < `stats_min_samples`（默认 2）时返回"无判断"，既不加分也不扣分。
  避免"跑过一次失败就被永久打上低置信标签"。

查看方式：`python main_task.py --health`（与元素库体检合并在一起）。

## 9. 现场输出怎么读

一次正常运行：

```
▶ 开始回放：共 12 步
   置信度评估：观察模式 —— 只评分与告警，绝不打断
   环境守卫 + 检查点回滚：已启用
  ✅ 步骤 1/12  [打开网页 https://erp.example.com] {T2(cdp)}  置信 4.75/5 高 ✅
  ✅ 步骤 2/12  [录入「admin」→【用户名】] {T2(cdp)}  置信 5.00/5 高 ✅
  ...
  ⚠️ 步骤 9/12  [click_elem【导出】] {T4(coord)}  置信 2.10/5 偏低 ⚠️
       [基准 1.8] T4 路径（屏幕坐标，最脆弱）
       [-0.40] 最近有 1 次未命中记录
       [+0.30] 配了结果校验（失败会被发现，不会假成功）
  ✅ 步骤 9/12  [click_elem【导出】] {T4(coord)}  置信 2.10/5 偏低 ⚠️

🎉 全部 12 步执行完成。
   置信度：平均 4.21/5（高 9 / 中 2 / 偏低 1 / 极低 0），人工介入 0 次
   ⚠️ 有 1 步置信度偏低，建议 `python main_task.py --health` 体检元素库
```

读法：
- 只有偏低/极低的步骤会展开归因（正常的只打一行）——**不给你添噪音**
- 结尾的汇总告诉你"这次跑得稳不稳"，`偏低` 那几步就是**下次该优化的地方**

一次失败：

```
❌ 步骤 12 已重试 3 次仍失败，任务暂停。
   最后错误：步骤11异常：按钮被遮挡，点击无效
   🔎 环境诊断：页面状态正常 → 问题更可能出在这一步的元素定位或业务前置条件。
   （已尝试过更换定位策略、修复页面环境等替代做法，说明不是偶发抖动）
   👉 建议：`python main_task.py --health` 体检元素库；确认前置条件后从该步续跑。
```

诊断会先排除环境问题，再指向元素/业务问题——**帮你少走弯路**。

## 10. FAQ

**Q1：这会不会让我的流程变得经常弹窗、没人守着就卡住？**
不会。默认是 `shadow` 模式，**从不打断**。只有你主动改成 `adaptive` 才会弹窗。
而且 `interactive_timeout`（默认 60 秒）到时会自动选默认项——
偏低置信默认"继续执行"，极低置信默认"暂停"（保守），不会永久卡死。

**Q2：置信度低是不是意味着一定会失败？**
不是。它表达的是"**这一步的不确定性**"，不是"一定失败"。
一个 T4 坐标点击可能每次都成功，但它**依然该被标记**——因为一旦界面微调，它就会静默点错。

**Q3：会不会增加很多耗时？**
每步多一次 CDP 往返（浅检环境）+ 一次定位探测（复用给执行，不额外算）。
实测都是毫秒级。整个流程几十步，影响在几百毫秒内。

**Q4：置信度太严/太松怎么办？**
改 `confirm_below` / `auto_above` 两个阈值即可，见 §4。

**Q5：`step_stats.json` / `checkpoints.json` 要提交到 git 吗？**
不要。它们是运行产物，已在 `.gitignore` 里。

**Q6：我不想用这些功能，能彻底关掉吗？**
能。`confidence.enabled=false` 或 `mode="off"`。此时行为与 v3.4.x 完全一致
（这一点有专门的回归测试 `E9b` 守着）。

## 11. 学术溯源对照表

本模块每个机制都能对应到具体研究（见 `dive-into-llms` 第 9 章 GUI 智能体）：

| 本技能机制 | 来源 | 论文做法 | 我们的确定性替代 |
|---|---|---|---|
| 置信度评分 | OS-Kairos（ACL 2025） | 模型输出 1~5 分 | 8 类客观信号加权合成 |
| 自适应介入 | 同上 | 低于阈值请求人类介入 | 弹窗三选一（继续/跳过/暂停） |
| 环境劫持检测 | OS-Kairos + Caution for the Environment | 模型识别环境干扰 | URL 特征 + 一次 DOM 探测 |
| 策略轮换重试 | OS-Kairos（反 over-execution） | 模型重新规划 | 换定位策略 / 修环境 |
| 检查点回滚 | Explicit Rollback Mechanisms | 显式回退机制 | URL 级轻量检查点 |
| 元素库自动遗忘 | GEM（OOD 检测）+ GUI-Agent-Harness | 嵌入建模检测 OOD | 连续未命中计数（v3.4.1 已实现） |
| 步骤战绩先验 | AppAgentX（记忆捷径节点） | 学习并记忆行为模式 | 按指纹累计成功率 |
| 指令模糊时发问 | Navi-plus（Follow-up Questions） | 主动追问补全信息 | 多匹配检测 → 归因提示「可能点错」 |

**共同的取舍**：论文用模型解决，我们用确定性信号解决。
代价是能力上限低（处理不了"语义模糊的自然语言指令"），
但换来的是**在 2 核 8GB 无独显的机器上真的能跑、且每次结果一样**。
